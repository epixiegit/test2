# 분석·웹서버 검증 순서와 체크리스트

[시작 안내](README.md) · [분석 예시](02_분석검증_예시.md) · [AI 요청문](04_AI에게시키는프롬프트.md)

## 검증은 무엇을 하는 일인가

- **검증:** 내가 해결하려던 문제가 실제로 해결됐는지 근거로 확인하는 일.
- **테스트:** 특정 입력을 넣고, 미리 정한 기대 결과와 실제 결과를 비교하는 작업.
- **기대값:** 정답이라고 판단하는 결과. 가능하면 요구사항·손계산·독립적인 기준에서 정한다.
- **단위 테스트:** 합계 계산처럼 작은 기능 하나를 확인하는 테스트.
- **API 테스트:** 화면을 거치지 않고 서버에 요청해 응답 코드와 내용을 확인하는 테스트.
- **화면 테스트:** 브라우저에서 입력·클릭·화면 변화까지 확인하는 테스트.
- **회귀 테스트:** 수정 이후 기존에 되던 기능이 깨지지 않았는지 다시 확인하는 테스트.

테스트가 모두 통과해도 업무 목표를 잘못 이해했다면 좋은 해결책이 아니다. 반대로 화면이 예뻐도 숫자와 데이터가 틀리면 실패다. 아래 순서로 둘 다 확인한다.

## 1. 무엇이 성공인지 먼저 정하기 — 사람 중심

- [ ] 누가, 어떤 상황에서, 무엇을 결정하려고 이 결과를 사용하는지 한 문장으로 설명할 수 있다.
- [ ] 필수 기능과 이번에 만들지 않을 범위를 구분했다.
- [ ] 금액·건수·기간·대상·제외 조건의 정의를 확인했다.
- [ ] 중요한 미확인 조건은 현업 담당자에게 질문하거나 가정으로 표시했다.
- [ ] 핵심 사용자 흐름을 하나 적었다. 예: 부서 선택 → 승인 금액 조회 → 같은 조건으로 CSV 다운로드.

**예시 합격 기준:** 취소 요청을 제외하고 승인된 구매 요청만 집계한다. 전체 합계는 35,000원, 품질 부서 합계는 5,000원이며 화면과 다운로드 값이 일치한다.

이 기준은 실습 데이터의 약속이다. 다른 과제에도 그대로 적용할 규칙은 아니다.

## 2. 원본 데이터를 이해하고 확인하기 — 사람/툴

- [ ] 한 행이 무엇을 의미하는지 확인했다. 주문 한 건인지, 주문의 품목 한 줄인지 구분한다.
- [ ] 필요한 열이 있고, 식별자·금액·날짜·분류 값의 형식이 맞는다.
- [ ] 중복 ID, 빈 값, 잘못된 값의 처리 기준을 정했다.
- [ ] 삭제·보정·제외 전후의 건수와 이유를 설명할 수 있다.
- [ ] 작은 샘플을 직접 세거나 계산해 정답을 확보했다.

**실패 예:** 같은 주문이 품목별로 여러 행인데 주문 총액을 행마다 더하면 금액이 부풀려진다. 오류 없이 코드가 실행돼도 틀린 결과다.

## 3. 분석 결과 확인하기 — 툴 실행 + 사람의 기준 확인

- [ ] 작은 샘플의 실제 결과가 독립적으로 정한 기대값과 일치한다.
- [ ] 부서별 합계와 전체 합계가 같은 포함 조건에서 일치한다.
- [ ] 필터를 바꾸면 건수와 금액이 올바르게 변한다.
- [ ] 빈 결과, 금액 0, 잘못된 입력도 정한 기준대로 처리한다.
- [ ] 원본 파일을 덮어쓰지 않고 결과를 만들었다.

숫자가 달라졌다는 사실만으로 정답을 바꾸지 않는다. **요구사항이 틀렸는지, 코드가 틀렸는지, 테스트 입력이 틀렸는지** 먼저 확인한다.

## 4. 서버의 응답 확인하기 — 툴

- [ ] 서버가 시작되고, 예상한 포트와 경로에서 응답한다.
- [ ] 정상 요청의 응답 내용이 기대값과 일치한다.
- [ ] 잘못된 입력은 이해할 수 있는 오류로 처리한다.
- [ ] 없는 경로, 빈 결과 등도 확인했다.
- [ ] 다운로드 파일을 다시 읽어 열·행·숫자를 확인했다.

**주의:** HTTP 상태 `200`은 요청 처리 성공을 뜻하는 신호다. 응답 안의 합계가 맞는지는 별도 확인해야 한다.

## 5. 실제 브라우저에서 사용하기 — 사람/툴

- [ ] 화면 열기 → 입력/선택 → 실행 → 결과 확인을 직접 끝까지 수행했다.
- [ ] 화면의 숫자가 분석·API의 기대값과 일치한다.
- [ ] 조건을 바꿔도 이전 결과가 그대로 남거나 잘못 섞이지 않는다.
- [ ] 빈 결과와 서버 오류가 사용자에게 구분되어 보인다.
- [ ] CSV 다운로드가 되며, 화면의 필터 조건과 파일 내용이 같다.
- [ ] 새로고침 후에도 필요한 화면을 사용할 수 있다.
- [ ] 확인한 화면 크기에서 입력창·버튼·결과가 잘리지 않는다.

브라우저 테스트 도구 예: Playwright. 버튼 클릭 후 화면에 기대한 값이 나타날 때까지 확인하는 기능을 제공한다. 단순한 고정 시간 대기보다 결과 조건을 확인하는 방식을 사용한다. [공식 설명](https://playwright.dev/docs/test-assertions)

## 6. 처음 실행하는 조건으로 확인하기 — 툴

- [ ] 이미 실행 중인 서버에 의존하지 않고, 문서의 실행 명령으로 다시 시작할 수 있다.
- [ ] 작업 경로·입력 파일·환경 변수·필수 패키지가 설명되어 있다.
- [ ] 시험 환경에서는 실제 포트·미리보기 경로로 접근할 수 있다.
- [ ] 제출할 파일에 실행에 필요한 데이터·설정이 포함되어 있다.
- [ ] 마지막 수정 이후 관련 테스트와 핵심 사용자 흐름을 다시 확인했다.

기존 서버가 살아 있어서 화면이 보이는 것과, 제출한 프로젝트가 새로 실행되는 것은 서로 다른 확인이다.

## 7. 판정과 증거 기록하기 — 사람/툴

- **통과:** 실제 실행 결과가 기대값과 일치함. 입력·명령·결과 근거를 남긴다.
- **실패:** 실제 결과가 기대값과 다름. 재현 방법과 차이를 남긴다.
- **미실행:** 도구·시간·환경 문제 등으로 실행하지 못함. 이유를 남긴다.
- **검토만:** 코드를 읽거나 설계를 검토했지만 실제 동작은 확인하지 않음.

예: `품질 필터 / 기대 1건·5,000원 / API 실제 1건·5,000원 / 통과 / 실행 시각과 결과 파일`.

증거는 필요한 만큼만 남긴다. 테스트 개수나 문서 분량을 늘리는 것보다 **중요한 주장에 실제 근거가 있는지**가 우선이다.

## 시간이 부족하면 무엇부터 볼까

1. 틀리면 목적 자체가 무너지는 핵심 숫자·판단 규칙.
2. 실제 사용자가 끝까지 수행할 핵심 흐름 하나.
3. 자주 생길 잘못된 입력·빈 결과.
4. 제출한 파일로 다시 실행되는지.

문구·색상·사소한 정리보다 위 항목을 먼저 확인하자는 준비용 우선순위다. 대회의 공식 채점표를 의미하지 않는다.

## 도구가 증명하는 범위

- Python `unittest`: 기대 결과와 실제 결과를 비교하는 자동 테스트 실행 도구. 업무 기준의 정답은 사람이 정해야 한다. [공식 설명](https://docs.python.org/3/library/unittest.html)
- FastAPI `TestClient`: 앱 코드에 요청을 보내 응답을 검사한다. 실제 서버 포트·브라우저 연결까지 확인했다는 뜻은 아니다. [공식 설명](https://fastapi.tiangolo.com/tutorial/testing/)
- Playwright: 브라우저의 실제 화면 동작을 검사한다. 테스트에서 다루지 않은 업무 조건까지 보장하지는 않는다. [공식 설명](https://playwright.dev/docs/test-assertions)
