# 웹서버 관련 검증 체크리스트 예시

[일반적인 검증](일반적인_검증_체크리스트_예시.md) · [코드 구현 검증](코드구현_관련_체크리스트_예시.md)

- FastAPI 백엔드·React 프론트와 같은 웹 프로젝트에 적용할 **검증 후보 100개**. 현재 프로젝트가 통과했다는 기록이 아님.
- 먼저 핵심 사용자 흐름에 필요한 항목을 선택. **100개 모두 수행할 필요는 없으며**, 로그인·DB·업로드·외부 API 등 없는 기능은 N/A(해당 없음)와 이유를 남김. 체크리스트를 채우려고 없는 기능을 새로 만들 필요는 없음.
- 실제 실행한 입력·기대값·실제값·증거를 [검증 기록 템플릿](05_검증기록_템플릿.md)에 기록. 실행하지 않은 항목은 미실행으로 두고, 체크 표시를 통과 증거로 대신하지 않음.
- 상태코드·타입·저장 정책·성능 기준은 해당 프로젝트 계약에 맞춰 정함. 아래 35,000원 등 수치는 예시이며, HTTP 200만으로 계산이 맞다고 판단하지 않음.
- 데이터 변경·오류·동시 요청 실험은 본인이 권한을 가진 테스트 서버·테스트 계정·복제 데이터에서 수행. 원본 업무 데이터에 실험하지 않음.

## 용어를 짧게 보면

- API: 화면이 서버에 보내는 요청 창구. 라우트: 요청 주소와 처리 함수의 연결. JSON: 요청·응답에 자주 쓰는 데이터 형식.
- 인증: 누구인지 확인. 권한: 그 사람이 무엇을 할 수 있는지 확인. 토큰·쿠키: 로그인 상태 전달 등에 쓰는 값.
- CORS: 브라우저가 다른 출처의 응답을 읽을 수 있는지에 관한 규칙. 프록시: 브라우저와 실제 서버 사이에서 요청을 전달하는 중간 서버.
- SPA: 화면 이동을 주로 브라우저 안에서 처리하는 앱. WebSocket·SSE: 서버의 새 데이터를 이어서 받는 통신 방식.

## 1. 실행 환경·서버 설정

- [ ] WEB-001 README의 서버 시작 명령을 승인된 프로젝트 가상환경에서 실행한다 → 추가 수동 조작 없이 서버가 뜨고 시작 오류가 없어야 한다.
- [ ] WEB-002 실행 로그의 호스트·포트와 접속 주소를 대조한다 → 예를 들어 백엔드가 8000번이면 프론트 설정·API 요청도 같은 백엔드를 가리켜야 한다.
- [ ] WEB-003 [웹 IDE] 외부 미리보기가 필요한 서버를 지정된 호스트에 바인딩한다 → 0.0.0.0 바인딩과 플랫폼의 실제 미리보기 주소로 접속까지 확인한다.
- [ ] WEB-004 필수 환경변수 하나를 뺀 별도 테스트 설정으로 시작한다 → 필요한 값의 이름을 알리고 시작을 중단하거나 문서에 정한 제한 모드로 동작해야 한다.
- [ ] WEB-005 포트·URL 등 설정에 잘못된 값을 넣는다 → 원인을 알 수 있는 오류가 나고, 엉뚱한 주소로 조용히 연결하지 않아야 한다.
- [ ] WEB-006 데이터·정적 파일의 경로가 다른 실행 위치에서도 맞는지 확인한다 → 문서에서 허용한 시작 위치에서 같은 파일을 읽고 파일 없음 오류가 없어야 한다.
- [ ] WEB-007 사용 중인 포트로 두 번째 서버를 실행한다 → 포트 충돌을 명확히 알리고, 첫 번째 서버를 임의 종료하거나 다른 포트로 조용히 바꾸지 않아야 한다.
- [ ] WEB-008 데이터 폴더가 없거나 읽을 수 없는 테스트 상황에서 시작한다 → 무관한 빈 데이터로 정상처럼 동작하지 않고 필요한 경로·원인을 알려야 한다.
- [ ] WEB-009 개발용 환경변수를 바꾼 후 필요한 재시작·재빌드를 수행한다 → 실제 요청 대상과 동작이 변경값을 사용하며 오래된 설정이 남지 않아야 한다.
- [ ] WEB-010 연습 서버를 정상 종료한다 → 해당 포트가 해제되고 자식 서버 프로세스가 남지 않아 같은 포트로 다시 실행할 수 있어야 한다.

## 2. 라우트·HTTP 요청 계약

- [ ] WEB-011 문서에 있는 각 API의 경로와 HTTP 메서드로 요청한다 → 핵심 경로 모두 약속한 응답을 내고 라우터 등록 누락이 없어야 한다.
- [ ] WEB-012 GET 전용 API에 POST 같은 허용하지 않은 메서드를 보낸다 → 보통 405 등 명시된 거절 응답을 내고 데이터가 변경되지 않아야 한다.
- [ ] WEB-013 존재하지 않는 API 경로를 요청한다 → 404를 반환하고 내부 예외인 500이나 성공인 200으로 처리하지 않아야 한다.
- [ ] WEB-014 경로 끝의 슬래시 유무를 바꿔 요청한다 → 허용·리다이렉트·거절 정책이 일관되고, 저장 요청이 중복 실행되지 않아야 한다.
- [ ] WEB-015 숫자 ID 경로에 문자나 범위 밖 ID를 전달한다 → 400·422 또는 문서에 정한 응답으로 거절하고 서버가 멈추지 않아야 한다.
- [ ] WEB-016 조회용 GET 요청을 여러 번 반복한다 → 조회가 저장·삭제·카운터 중복 반영 같은 의도하지 않은 상태 변경을 만들지 않아야 한다.
- [ ] WEB-017 쿼리 조건을 생략한 요청과 빈 문자열 조건을 전달한 요청을 비교한다 → 기본값·빈 조건의 의미가 요구사항대로 구분되어야 한다.
- [ ] WEB-018 같은 쿼리 키를 두 번 보낸다 → 예를 들어 department=생산과 department=품질을 함께 보냈을 때 목록 처리·하나 선택·거절 중 정한 동작과 일치해야 한다.
- [ ] WEB-019 한글·공백·특수문자가 있는 검색어를 URL 인코딩해 전달한다 → 백엔드가 원래 값으로 받아 검색하며 문자가 깨지거나 조건이 잘리지 않아야 한다.
- [ ] WEB-020 JSON 전용 API에 지원하지 않는 본문 형식을 보낸다 → 명시한 4xx 응답으로 처리하며, 폼·일반 문자열을 엉뚱한 JSON 값으로 받아들이지 않아야 한다.

## 3. 입력 검증·파일 업로드

- [ ] WEB-021 필수 요청 필드를 하나씩 빼서 보낸다 → 누락된 필드를 식별하는 오류가 나고 계산·저장이 실행되지 않아야 한다.
- [ ] WEB-022 금액 필드에 문자열·배열·불리언 등 허용하지 않은 타입을 보낸다 → 계약에 맞게 거절하며 true를 1원처럼 잘못 해석하지 않아야 한다.
- [ ] WEB-023 최소·최대 길이가 정해진 문자열에 경계 길이와 초과 길이를 보낸다 → 허용 범위만 처리하고 초과 입력은 정한 오류로 거절해야 한다.
- [ ] WEB-024 수량·금액 등 숫자 필드에 0·최솟값·최댓값·범위 밖 값을 보낸다 → 정한 포함·제외 경계와 일치해야 한다.
- [ ] WEB-025 null·빈 문자열·공백만 있는 문자열을 각각 보낸다 → 값 없음과 실제 값의 처리 기준이 명확하고, 필수 값이 공백으로 통과하지 않아야 한다.
- [ ] WEB-026 상태값에 승인·취소 등 허용 목록 밖의 값을 보낸다 → 알 수 없는 상태를 임의로 승인 처리하지 않고 거절해야 한다.
- [ ] WEB-027 배열 요청의 두 번째 행에 잘못된 필드를 넣는다 → 어느 행·필드가 문제인지 알 수 있고, 부분 저장 여부가 정한 정책과 일치해야 한다.
- [ ] WEB-028 [업로드] 허용한 확장자라도 실제 내용이 다른 파일을 전달한다 → 파일 내용 파싱·검증 단계에서 거절하고 실행 파일 등으로 취급하지 않아야 한다.
- [ ] WEB-029 [업로드] 빈 파일과 설정된 크기를 넘는 파일을 각각 전달한다 → 빈 파일·용량 초과를 구분해 알리고 무한 대기나 불완전 파일 저장이 없어야 한다.
- [ ] WEB-030 [업로드] 상위 경로 표시나 중복 이름이 포함된 파일명을 전달한다 → 지정 저장 폴더 밖에 쓰지 않으며 기존 파일을 덮어쓰는 정책을 명확하게 적용해야 한다.

## 4. 응답 내용·오류 처리

- [ ] WEB-031 손으로 기대값을 정한 작은 데이터로 집계 API를 호출한다 → HTTP 200뿐 아니라 건수·합계가 기대값과 일치해야 한다. 예: 승인 5건·35,000원.
- [ ] WEB-032 성공 JSON의 필수 키와 값 타입을 검사한다 → 프론트가 기대하는 record_count가 빠지거나 숫자 대신 뜻밖의 문자열로 오지 않아야 한다.
- [ ] WEB-033 API의 금액·비율·거리 단위를 화면과 대조한다 → 원/천 원, 0.1/10% 같은 단위 변환이 한 번만 적용되어야 한다.
- [ ] WEB-034 날짜·시간 응답을 시간대가 다른 브라우저에서 읽어본다 → 시간대 정보와 표시 정책이 일치하고 날짜가 의도치 않게 하루 바뀌지 않아야 한다.
- [ ] WEB-035 계산 불능 값이 생기는 입력을 보낸다 → NaN·Infinity 등 처리 불가능한 값을 JSON 응답에 그대로 넣지 말고 정한 null·오류 정책을 적용해야 한다.
- [ ] WEB-036 알려진 잘못된 입력으로 요청한다 → 오류를 HTTP 200의 성공 데이터처럼 반환하지 않고, 프론트가 구분할 수 있는 상태와 오류 내용을 반환해야 한다.
- [ ] WEB-037 테스트 환경에서 내부 예외를 유발한다 → 적절한 5xx 응답을 내고 전체 서버가 종료되거나 다른 정상 요청까지 실패하지 않아야 한다.
- [ ] WEB-038 오류 응답 본문을 확인한다 → 사용자가 수정할 필드·행동은 알려주되 비밀번호·토큰·서버 파일 경로·전체 스택 추적을 노출하지 않아야 한다.
- [ ] WEB-039 [외부 API] 의존 서비스가 응답하지 않는 상황을 재현한다 → 정해진 제한 시간 후 오류를 반환하고 요청이 끝없이 연결 상태로 남지 않아야 한다.
- [ ] WEB-040 오류 한 건의 브라우저 요청과 서버 로그를 대조한다 → 요청 시각·경로·식별자 등으로 같은 실패를 찾아 원인을 추적할 수 있어야 한다.

## 5. 저장·DB·파일 상태 — 해당 기능이 있을 때

- [ ] WEB-041 테스트 항목을 생성한 뒤 조회 API로 다시 읽는다 → 반환된 ID로 같은 항목이 조회되고 저장된 필드가 입력과 일치해야 한다.
- [ ] WEB-042 항목의 한 필드만 수정한 뒤 다시 읽는다 → 수정 대상만 바뀌고 보내지 않은 기존 필드는 정책에 맞게 보존되어야 한다.
- [ ] WEB-043 테스트 항목을 삭제한 뒤 재조회한다 → 삭제 정책에 따라 조회에서 제외되거나 404가 나며 다른 항목은 그대로 남아야 한다.
- [ ] WEB-044 영구 저장이 필요한 데이터를 넣고 서버를 재시작한다 → 같은 데이터가 유지되어야 한다. 메모리 전용 데모라면 유지하지 않는 범위를 문서에 명시한다.
- [ ] WEB-045 여러 테이블을 함께 바꾸는 작업의 중간 단계를 테스트용으로 실패시킨다 → 한 작업으로 보장한 변경은 전체 취소되어 반쪽 저장이 남지 않아야 한다.
- [ ] WEB-046 유일해야 하는 ID·이메일 등을 중복 생성한다 → 정의한 충돌 응답을 내며 DB에 중복 행이 생기지 않아야 한다.
- [ ] WEB-047 조회 API에 필터와 정렬을 함께 적용한다 → 저장된 테스트 데이터 중 조건에 맞는 항목만 정해진 순서로 반환해야 한다.
- [ ] WEB-048 변경 없는 테스트 데이터에서 여러 페이지를 연속 조회한다 → 안정된 정렬 기준에서 항목이 중복되거나 누락되지 않고 마지막 페이지·빈 페이지도 정상 처리되어야 한다.
- [ ] WEB-049 새 항목 생성·수정 후 생성 시각과 수정 시각을 읽는다 → 생성 시각이 매 조회마다 바뀌지 않고 수정 시각은 실제 변경 정책에 맞게 갱신되어야 한다.
- [ ] WEB-050 테스트 저장소의 쓰기 실패를 재현한다 → 성공 응답을 보내지 않으며 기존 파일을 빈 파일·잘린 파일로 남기지 않아야 한다.

## 6. 로그인·접근 권한·노출 — 해당 기능이 있을 때

- [ ] WEB-051 로그인 없이 보호된 API를 호출한다 → 정한 인증 오류로 거절하고 보호된 데이터를 반환하지 않아야 한다.
- [ ] WEB-052 만료되거나 변조된 인증 정보를 전달한다 → 정상 사용자로 처리하지 않고 재로그인 등 필요한 안내를 할 수 있어야 한다.
- [ ] WEB-053 사용자 A로 사용자 B의 항목 ID를 조회한다 → 소유권 정책에 따라 거절하고 B의 내용을 노출하지 않아야 한다.
- [ ] WEB-054 사용자 A로 사용자 B의 항목을 수정·삭제한다 → 서버가 거절하고 B의 실제 저장 데이터가 바뀌지 않아야 한다.
- [ ] WEB-055 일반 계정으로 관리자 API를 직접 호출한다 → 화면에서 버튼을 숨기는 것과 별개로 서버에서도 관리자 작업을 거절해야 한다.
- [ ] WEB-056 로그아웃·계정 정지 후 이전 인증 정보로 재요청한다 → 서비스가 정한 세션 폐기·토큰 유효기간 정책대로 접근이 제한되어야 한다.
- [ ] WEB-057 [쿠키 인증] 실제 접속 환경에서 인증 쿠키 속성을 확인한다 → HTTPS 여부와 로그인 흐름에 맞는 Secure·HttpOnly·SameSite 정책이 적용되어야 한다.
- [ ] WEB-058 브라우저에 내려간 JS 파일·설정 응답·일반 API 응답을 검색한다 → 서버 전용 API 키·DB 비밀번호 등 비밀값이 포함되지 않아야 한다.
- [ ] WEB-059 [DB 검색] 따옴표 등 SQL처럼 보이는 검색 문자열을 보내고 쿼리 코드를 확인한다 → 값을 SQL 명령문에 직접 이어 붙이지 않고 매개변수로 전달하며, 검색 범위 우회나 다른 행 변경이 없어야 한다.
- [ ] WEB-060 [사용자 입력 표시] 제목에 `<b>테스트</b>` 같은 문자열을 저장해 표시한다 → 일반 텍스트 필드는 HTML로 실행·해석되지 않아야 한다. 의도한 서식 입력은 별도 정화 정책을 확인한다.

## 7. React와 API 연결

- [ ] WEB-061 브라우저 Network에서 실제 API 요청 URL을 본다 → 백엔드 주소·포트·경로를 가리키고 프론트 정적 서버에 잘못 요청하지 않아야 한다.
- [ ] WEB-062 개발 화면과 빌드된 화면에서 같은 기능을 실행한다 → 두 환경 모두 올바른 API 기본 주소를 사용하고 개발 PC 전용 주소가 배포 화면에 남지 않아야 한다.
- [ ] WEB-063 [서로 다른 출처] 허용된 프론트 주소에서 API를 호출한다 → 실제 브라우저가 응답을 읽을 수 있으며 CORS 오류가 없어야 한다.
- [ ] WEB-064 [CORS 제한] 허용하지 않은 출처에서 브라우저 요청을 시도한다 → 브라우저가 응답을 읽지 못해야 한다. CORS 자체를 서버 인증·권한 검사로 대신하지 않는다.
- [ ] WEB-065 [인증 필요] 프론트의 실제 요청 헤더·쿠키를 확인한다 → 필요한 인증 정보가 전달되며 URL 쿼리나 불필요한 로그에 토큰을 남기지 않아야 한다.
- [ ] WEB-066 프론트에서 JSON 저장 요청을 보낸다 → Content-Type과 본문 구조가 백엔드 계약에 맞고, 폼 상태의 숫자·null이 의도한 타입으로 전달되어야 한다.
- [ ] WEB-067 본문 없는 204 응답을 프론트에 전달한다 → 빈 본문을 JSON으로 해석하다 오류가 나지 않고 정상 완료 상태가 표시되어야 한다.
- [ ] WEB-068 백엔드가 4xx·5xx를 반환하도록 만든다 → 프론트가 성공 알림을 띄우지 않고 상태와 오류 내용을 구분해 안내해야 한다.
- [ ] WEB-069 화면을 떠나거나 요청을 취소한 뒤 응답이 도착하게 한다 → 사라진 화면을 업데이트하거나 취소를 일반 저장 성공처럼 처리하지 않아야 한다.
- [ ] WEB-070 백엔드가 합계 0·빈 문자열·null을 각각 반환하게 한다 → 프론트가 0을 값 없음으로 바꾸는 등 잘못된 기본값 처리를 하지 않아야 한다.

## 8. 실제 화면의 상태·사용 흐름

- [ ] WEB-071 응답을 일부러 늦춘 뒤 조회한다 → 조회 중 상태가 보이고 사용자가 처리 중인지 알 수 있어야 한다.
- [ ] WEB-072 결과가 없는 조건으로 바꾼다 → 빈 결과 안내와 0건 등이 표시되며 이전 조건의 표·합계가 남지 않아야 한다.
- [ ] WEB-073 한 번 오류를 발생시킨 뒤 정상 조건으로 다시 조회한다 → 재시도할 수 있고 성공 후 이전 오류 안내가 제거되어야 한다.
- [ ] WEB-074 저장 버튼을 빠르게 두 번 클릭한다 → 처리 중 버튼 잠금 등으로 의도하지 않은 중복 요청을 줄이고 결과가 두 번 저장되지 않아야 한다.
- [ ] WEB-075 필수 입력을 비우거나 형식을 틀리게 입력한다 → 어느 입력을 고칠지 화면에 안내하고, 잘못된 상태에서 성공 화면으로 넘어가지 않아야 한다.
- [ ] WEB-076 부서·기간 등 필터를 바꾼다 → 화면의 선택값, 실제 API 요청 조건, 결과 제목이 같은 조건을 나타내야 한다.
- [ ] WEB-077 현재 화면을 새로고침한다 → 필터를 유지하거나 초기화하는 정책과 실제 결과가 일치하고, 선택값만 남고 내용은 다른 조건이 되지 않아야 한다.
- [ ] WEB-078 [화면 이동] 브라우저 뒤로·앞으로 가기를 사용한다 → URL·선택 조건·화면 내용이 정한 탐색 방식에 맞게 복원되어야 한다.
- [ ] WEB-079 좁은 화면과 확대된 글자 크기로 주요 작업을 수행한다 → 핵심 버튼·오류 안내가 잘리지 않고 표가 필요하면 스크롤로 접근 가능해야 한다.
- [ ] WEB-080 필터를 적용해 CSV·Excel 등을 내려받고 실제 파일을 다시 연다 → 화면과 같은 조건·행 수·합계이며 한글·숫자 타입·빈 값 표시가 의도와 같아야 한다.

## 9. 동시 요청·오래 걸리는 작업·성능

- [ ] WEB-081 조건 A를 조회한 직후 B를 조회하고 A 응답을 더 늦게 도착시킨다 → 최종 화면은 가장 최근 선택인 B의 결과를 유지해야 한다.
- [ ] WEB-082 [중복 방지 계약] 같은 저장 요청이나 같은 요청 식별자를 재전송한다 → 서버 차원에서도 중복 생성·결제·작업 등록이 발생하지 않아야 한다.
- [ ] WEB-083 [동시 편집] 같은 항목에 서로 다른 변경을 동시에 보낸다 → 버전 충돌 거절 또는 정한 갱신 정책이 적용되고 변경이 조용히 유실되지 않아야 한다.
- [ ] WEB-084 서로 다른 테스트 사용자·세션에서 다른 조건을 동시에 요청한다 → 한 사용자의 필터·파일·결과가 다른 사용자에게 섞이지 않아야 한다.
- [ ] WEB-085 같은 조회를 정한 횟수만큼 반복하며 자원 사용을 확인한다 → 메모리·파일 핸들·DB 연결이 계속 누적되는 현상이 없어야 한다.
- [ ] WEB-086 오래 걸리는 작업을 실행한다 → 완료까지 상태를 알 수 있고, 제한 시간이 지나면 실패·백그라운드 작업 등 정한 방식으로 전환되어야 한다.
- [ ] WEB-087 [취소 기능] 실행 중인 작업을 취소한다 → 취소 이후 결과 게시·저장 여부가 정한 정책과 일치하고 완료로 잘못 표시하지 않아야 한다.
- [ ] WEB-088 예상 최대 크기의 테스트 데이터로 응답 시간을 측정한다 → 미리 정한 목표 안에 들어야 한다. 예: 목표가 2초라면 측정값과 측정 조건을 함께 기록한다.
- [ ] WEB-089 정상·오류 요청을 소규모로 함께 보낸다 → 일부 실패 때문에 정상 요청이 모두 멈추지 않고 연결이 이후에도 정상 처리되어야 한다.
- [ ] WEB-090 [외부 API 재시도] 의존 서비스의 실패를 반복시킨다 → 재시도 횟수·대기 시간에 상한이 있고 중복 작업이나 무한 요청 폭증이 없어야 한다.

## 10. 실제 배포·프록시·운영 확인

- [ ] WEB-091 제출할 프론트 빌드를 실제 제공 방식으로 열어본다 → 첫 화면의 JS·CSS·이미지가 정상 로드되며 빌드 성공만으로 통과 처리하지 않아야 한다.
- [ ] WEB-092 [SPA 경로] 상세 화면 주소를 직접 열고 새로고침한다 → 필요한 프론트 경로가 열리되, 잘못된 API 주소까지 HTML 200으로 바뀌지 않아야 한다.
- [ ] WEB-093 [경로 접두어] 플랫폼이 /preview/app 같은 하위 경로로 제공한다면 그 주소에서 실행한다 → 정적 파일·라우터·API 경로가 실제 배포 경로에 맞아야 한다.
- [ ] WEB-094 [HTTPS 제공] 실제 공개 화면의 Network와 Console을 확인한다 → HTTP API·파일 호출 때문에 혼합 콘텐츠 오류가 발생하지 않아야 한다.
- [ ] WEB-095 [프록시] 프록시를 거친 요청의 원래 호스트·프로토콜 처리를 확인한다 → 외부 주소로 접근했을 때 내부 주소로 잘못 리다이렉트되지 않아야 한다.
- [ ] WEB-096 [브라우저 사전 요청] JSON·인증 헤더 요청의 OPTIONS 사전 요청을 확인한다 → 허용한 메서드·헤더를 통과시켜 실제 요청이 이어져야 한다.
- [ ] WEB-097 [WebSocket·SSE] 실제 미리보기 주소에서 연결·메시지 수신·끊김을 확인한다 → 프록시를 지나도 데이터가 오고 재연결 또는 종료 안내가 정한 대로 동작해야 한다.
- [ ] WEB-098 [상태 확인 API] DB 등 필수 의존성을 사용할 수 없게 한 테스트에서 상태 API를 호출한다 → 프로세스 생존과 서비스 준비 여부를 구분해 잘못된 준비 완료를 알리지 않아야 한다.
- [ ] WEB-099 제출 폴더를 새 환경에 가져와 문서대로 의존성 설치·시작을 수행한다 → 로컬의 숨은 파일·개인 절대 경로·미기록 환경 설정 없이 실행 가능해야 한다.
- [ ] WEB-100 최종 제출 경로와 실제 실행 프로세스를 대조하고 핵심 사용자 흐름을 한 번 수행한다 → 이전 복사본을 실행한 것이 아니며 제출한 코드로 조회·필터·필요한 저장·내려받기가 동작해야 한다.

## 공식 문서와 사용 범위

- [FastAPI Testing](https://fastapi.tiangolo.com/tutorial/testing/): TestClient로 상태코드·응답 내용을 확인하는 방법. 실제 서버 포트 연결과 브라우저 확인은 별도로 수행.
- [FastAPI CORS](https://fastapi.tiangolo.com/tutorial/cors/): 출처와 허용 출처·메서드·헤더 설정. CORS는 브라우저의 출처 간 응답 접근과 관련되며 사용자 인증을 대신하지 않음.
- [Playwright Assertions](https://playwright.dev/docs/test-assertions): 실제 화면의 텍스트·값·상태가 기대 조건에 도달했는지 확인하는 방법.

이 목록은 위 도구 사용법과 웹 요청·저장·화면 흐름을 바탕으로 구성한 실무 검증 예시이며, 특정 대회의 공식 채점표가 아님.
