01

백엔드 내부

FastAPI가 요청을 나누고, 함수들이 DB 연결을 사용해 조회·저장.
상단은 서버 초기화, 하단은 요청마다 실행되는 업무 흐름. 화살표는 호출·사용 방향이며 모든 노드가 한 줄로 실행되는 것은 아님.

BACKEND / CALL & DATA FLOW
읽는 순서 초기화(위) → 요청 분기(왼쪽) → 처리 함수(가운데) → DB(오른쪽)노드 클릭 / Tab + Enter로 상세 보기

connection()은 업무 로직이 아님. 연결·commit·rollback·close를 관리하고, SQL은 각 핸들러와 stock_rows()가 실행. 응답은 호출한 경로로 돌아가며 전체 왕복은 03번에서 확인.

백엔드 폴더·파일·전체 함수 설명
SQLite 테이블 4개와 연결 관계
위치별 재고locations.code ← inventory.location · inventory.sku → products.sku이력 참조locations.code ← movements.location · movements.sku → products.sku
테이블역할주요 연결과 변경
locations보관 위치 코드·구역·분류초기 샘플 위치. 재고와 이력이 위치를 참조
productsSKU·이름·단위·안전재고·version품목 등록/수정. 등록만으로 위치별 재고가 생기지는 않음
inventory위치+SKU별 수량·version입출고·실사로 변경. 위치+SKU별 한 행
movements변경 종류·전후 수량·작업자·시각재고 변경과 같은 트랜잭션에서 이력 추가
02

프론트엔드 내부

App이 상태를 보관하고, 조회 결과와 사용자 입력으로 화면을 다시 그림.
현재 컴포넌트·폼·API 함수는 대부분 App.jsx 한 파일에 공존. 아래 노드는 함수·개념 단위이며 각각 별도 파일이라는 뜻은 아님.

FRONTEND / COMPONENT, STATE & EVENT FLOW
핵심 순환 load → api → setData → 화면 / 폼 저장 → saved → load검색·메뉴 선택은 받은 데이터에서 처리

화면 조작마다 서버를 요청하는 구조는 아님. 메뉴·검색·필터·위치 선택은 프론트 상태를 변경. 첫 조회·새로고침·저장 후 재조회에서 load() 실행. CSV는 브라우저가 직접 다운로드.

03

프론트 ↔ 백엔드 연결

왼쪽은 브라우저, 오른쪽은 서버와 DB. 위에서 아래로 시간이 흐름.
조회·저장·다운로드를 각각 따라볼 수 있음. 저장 응답 뒤에 별도의 조회 요청이 다시 발생하는 점을 확인.

일반 실행브라우저 → FastAPI :8000 → / 는 dist/index.html · /assets 는 빌드 파일 · /api 는 업무 처리개발 실행브라우저 → Vite :5173 → /api 프록시 → FastAPI :8000 → SQLite빌드 단계frontend/src + styles.css → Vite build → frontend/dist (실행 전 파일 생성 단계)
시간 순서 위 → 아래 · 화살표 문구 선택 → 단계별 입출력 설명초록: 요청 / 파랑: 응답·갱신
