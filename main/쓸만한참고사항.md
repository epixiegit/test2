superpowers

**1. `brainstorming` — 요구사항과 설계 방향 정리**

- **용도:** 무엇을 만들지, 어떤 기능이 필요한지 구현 전에 정리합니다. 중요한 미결정 사항을 질문하고 설계 방향을 합의합니다.
- **예시:** “brainstorming을 사용해서 사내 문서 검색 웹의 요구사항을 정리해줘. 직원들이 문서를 쉽게 찾는 데 필요한 핵심 기능부터 정하고 싶어.”

**2. `writing-plans` — 구체적인 구현 계획 작성**

- **용도:** 정해진 설계를 구현 순서로 바꿉니다. 수정할 파일, 작업 내용, 검증 방법을 정리합니다.
- **예시:** “writing-plans를 사용해서 승인한 설계를 구현 계획으로 만들어줘. FastAPI API와 React 화면을 어떤 순서로 만들지 정리해줘.”

**3. `executing-plans` — 현재 세션에서 계획 실행**

- **용도:** 현재 Agent가 계획을 작업별로 수행합니다. 작업마다 구현 Agent를 새로 띄우는 대신 현재 맥락을 유지하며 진행하고 마지막에 전체 리뷰를 합니다.
- **예시:** “executing-plans를 사용해서 이 구현 계획을 현재 세션에서 진행해줘. 단계별 검증 결과도 남겨줘.”

**4. `subagent-driven-development` — 작업별 Agent를 활용한 구현**

- **용도:** 계획의 각 작업을 별도 구현 Agent에 맡기고, 작업마다 요구사항 충족 여부와 코드 품질을 검토합니다. 마지막에는 전체 변경도 리뷰합니다.
- **예시:** “subagent-driven-development로 이 계획을 구현해줘. 각 작업이 끝나면 요구사항과 코드 품질을 검토해줘.”

**5. `dispatching-parallel-agents` — 독립적인 작업을 병렬 처리**

- **용도:** 서로 의존하지 않는 문제를 여러 Agent가 동시에 조사하거나 처리하게 합니다.
- **예시:** “dispatching-parallel-agents를 사용해서 프론트엔드 테스트 실패와 백엔드 테스트 실패를 각각 조사해줘. 우선 수정 없이 원인만 보고해줘.”

**6. `test-driven-development` — 테스트를 먼저 작성하는 개발**

- **용도:** 실패하는 테스트를 먼저 만들고, 통과하도록 구현한 뒤 코드를 정리합니다. `RED → GREEN → REFACTOR` 흐름입니다.
- **예시:** “test-driven-development를 사용해서 파일 업로드 용량 제한을 구현해줘. 제한을 넘는 파일을 거부하는 테스트부터 작성해줘.”

**7. `systematic-debugging` — 근본 원인을 찾는 디버깅**

- **용도:** 오류를 재현하고 로그·최근 변경·정상 동작과의 차이를 조사한 뒤, 가설을 검증하며 원인을 좁힙니다.
- **예시:** “systematic-debugging을 사용해줘. 검색 버튼을 누르면 간헐적으로 결과가 사라져. 재현 조건과 원인을 확인한 다음 수정해줘.”

**8. `verification-before-completion` — 완료 선언 전 검증**

- **용도:** “완료했다”, “고쳤다”, “테스트가 통과했다”고 말하기 전에 실제 검증을 실행하고 결과를 확인합니다.
- **예시:** “verification-before-completion을 적용해서 업로드와 검색이 실제로 동작하는지 확인해줘. 실행한 검사와 확인하지 못한 부분도 알려줘.”

**9. `requesting-code-review` — 코드 리뷰 요청·진행**

- **용도:** 구현 결과를 리뷰어 Agent에게 전달해 요구사항 충족 여부와 문제를 점검합니다.
- **예시:** “requesting-code-review를 사용해서 이번 검색 기능 변경을 리뷰해줘. 요구사항 누락과 기존 기능을 깨뜨릴 수 있는 부분을 확인해줘.”

**10. `receiving-code-review` — 받은 리뷰 의견 검토**

- **용도:** 다른 사람이나 Agent가 준 리뷰 의견이 기술적으로 타당한지 확인한 뒤 반영합니다. 불명확한 의견은 먼저 해석과 근거를 확인합니다.
- **예시:** “receiving-code-review를 사용해서 아래 리뷰 의견을 검토해줘. 현재 코드에도 해당하는 문제인지 확인하고 타당한 수정만 반영해줘.”

**11. `using-git-worktrees` — 독립된 작업 공간 준비**

- **용도:** 현재 작업과 분리된 공간에서 기능을 개발하도록 준비합니다. 이미 격리된 작업 공간이 있는지도 먼저 확인합니다.
- **예시:** “using-git-worktrees를 사용해서 로그인 기능을 개발할 별도 작업 공간을 준비해줘.”

**12. `finishing-a-development-branch` — 개발 브랜치 마무리**

- **용도:** 구현과 테스트가 끝난 뒤 병합, PR 생성, 브랜치 보관 등 마무리 방법을 정리하고 선택에 따라 처리합니다.
- **예시:** “finishing-a-development-branch를 사용해서 이번 작업을 마무리해줘. 테스트 상태를 확인하고 병합 또는 PR 생성 선택지를 알려줘.”

**13. `diagnosing-superpowers` — Superpowers 작업 과정의 문제 조사**

- **용도:** 작업 반복, 계획 무시, Skill 미작동, 과도한 시간·비용 같은 현상을 세션 기록에서 조사하고 근거를 정리합니다.
- **예시:** “diagnosing-superpowers를 사용해서 이번 세션에서 같은 파일을 반복 수정한 과정을 조사해줘. 기록 근거와 개선할 점을 알려줘.”

**14. `writing-skills` — 새로운 Skill 작성·수정·검증**

- **용도:** 반복해서 사용할 작업 절차를 Skill로 만들거나, 기존 Skill을 수정하고 제대로 작동하는지 확인합니다.
- **예시:** “writing-skills를 사용해서 FastAPI API를 검토하는 Skill을 만들어줘. 입력 검증, 응답 형식, 오류 처리를 확인하도록 하고 싶어.”

**15. `using-superpowers` — 적절한 Skill을 선택하는 기본 안내**

- **용도:** 작업에 어떤 Skill이 필요한지 판단하고, 해당 지침을 찾아 적용하도록 안내합니다. Superpowers의 진입 규칙에 해당합니다.
- **예시:** “using-superpowers에 따라 이번 작업에 필요한 Skill을 골라줘. 기존 React 앱에 파일 업로드 기능을 추가하려고 해.”

처음에는 **`brainstorming` → `writing-plans` → `executing-plans`**를 기본 흐름으로 익히고
오류가 나면 **`systematic-debugging`**, 끝날 때는 **`verification-before-completion`**을 사용하면 됩니다.
