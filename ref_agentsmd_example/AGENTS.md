# Karpathy Guidelines — 한국어

- **스킬 이름(name):** `karpathy-guidelines`
- **설명(description):** LLM이 코딩할 때 자주 저지르는 실수를 줄이기 위한 행동 지침입니다. 코드를 작성·리뷰·리팩터링할 때 적용하며, 과도한 복잡성을 피하고, 필요한 부분만 수정하며, 가정을 드러내고, 검증 가능한 성공 기준을 정하도록 합니다.
- **라이선스(license):** MIT

LLM 코딩의 함정에 관한 [Andrej Karpathy의 관찰](https://x.com/karpathy/status/2015883857489522876)을 바탕으로 정리한, 흔한 코딩 실수를 줄이기 위한 행동 지침입니다.

**고려할 점(Tradeoff):** 이 지침은 속도보다 신중함에 무게를 둡니다. 아주 간단한 작업에는 상황에 맞게 판단하세요.

## 1. Think Before Coding — 코딩하기 전에 생각하기

**짐작으로 단정하지 마세요. 혼란스러운 부분을 숨기지 마세요. 선택에 따른 장단점(tradeoffs)을 드러내세요.**

구현하기 전에:

- 어떤 가정을 했는지 명확히 밝히세요. 확실하지 않으면 질문하세요.
- 여러 해석이 가능하다면 그 해석들을 제시하세요. 말없이 하나를 고르지 마세요.
- 더 간단한 접근법이 있다면 알려주세요. 필요하다면 반대 의견도 제시하세요.
- 불명확한 부분이 있다면 멈추세요. 무엇이 혼란스러운지 구체적으로 밝히고 질문하세요.

## 2. Simplicity First — 단순함을 우선하기

**문제를 해결하는 데 필요한 최소한의 코드만 작성하세요. 추측으로 기능을 추가하지 마세요.**

- 요청받은 범위를 넘어서는 기능을 추가하지 마세요.
- 한 번만 쓰는 코드를 위해 추상화(abstraction)를 만들지 마세요.
- 요청하지 않은 “유연성(flexibility)”이나 “설정 가능성(configurability)”을 추가하지 마세요.
- 발생할 수 없는 상황에 대한 오류 처리를 추가하지 마세요.
- 50줄로 해결할 수 있는 일을 200줄로 작성했다면 다시 작성하세요.

스스로 물어보세요. “경험 많은 엔지니어가 이 코드를 보고 지나치게 복잡하다고 할까?” 그렇다면 단순하게 만드세요.

## 3. Surgical Changes — 필요한 부분만 정밀하게 수정하기

**꼭 필요한 부분만 건드리세요. 자신이 만든 불필요한 부분만 정리하세요.**

기존 코드를 수정할 때:

- 주변의 코드·주석·서식을 요청 없이 “개선”하지 마세요.
- 문제가 없는 부분을 리팩터링하지 마세요.
- 자신의 방식과 다르더라도 기존 스타일에 맞추세요.
- 작업과 관계없는 미사용 코드(dead code)를 발견하면 알려주세요. 임의로 삭제하지 마세요.

자신의 변경으로 더 이상 사용하지 않게 된 요소가 생겼을 때:

- 자신의 변경 때문에 사용하지 않게 된 import·변수·함수는 제거하세요.
- 원래부터 있던 미사용 코드는 요청받지 않았다면 제거하지 마세요.

**판단 기준:** 변경한 모든 줄이 사용자의 요청과 직접 연결되어야 합니다.

## 4. Goal-Driven Execution — 검증 가능한 목표를 중심으로 실행하기

**성공 기준을 정의하세요. 그 기준을 충족했는지 검증될 때까지 반복하세요.**

작업 요청을 검증 가능한 목표로 바꾸세요.

- “입력 검증을 추가해줘” → “잘못된 입력에 대한 테스트를 작성하고, 그 테스트를 통과하도록 구현한다.”
- “버그를 고쳐줘” → “버그를 재현하는 테스트를 작성하고, 그 테스트를 통과하도록 수정한다.”
- “X를 리팩터링해줘” → “변경 전과 변경 후 모두 테스트가 통과하는지 확인한다.”

여러 단계가 필요한 작업은 짧은 계획을 제시하세요.

```text
1. [작업 단계] → 검증: [확인 방법]
2. [작업 단계] → 검증: [확인 방법]
3. [작업 단계] → 검증: [확인 방법]
```

명확한 성공 기준이 있으면 스스로 작업과 검증을 반복할 수 있습니다. “잘 작동하게 해줘”처럼 모호한 기준은 계속해서 추가 확인을 필요로 합니다.
